<Section heading="What it is">

  <Prose nested>

  The knowledge base is the accumulated know-how a project draws on when
  planning: the rules it commits to, the shared vocabulary it speaks, how the
  system is built, the traps to avoid, what past work taught, and why decisions
  were made. Spektacular keeps it alongside your code, under
  `.spektacular/knowledge/`, so it lives and versions with the project.

  It is a **planning-time input**. When you ask Spektacular to plan a feature,
  the planning agent reads the relevant knowledge and writes the parts that
  matter straight into the plan. The implement workflow then works only from the
  plan documents (it never re-reads the knowledge base), so the plan is the
  contract.

  This is what it solves: without a knowledge base, every plan starts from a
  blank slate. The agent rediscovers your conventions, walks into gotchas you
  already mapped, and re-derives decisions you already made. Captured once and
  reused on every plan, the knowledge base is what lets Spektacular produce
  plans that fit *your* project instead of generic ones. It is also why you can
  trust the output enough to build on it.

  </Prose>

</Section>

<Section heading="The six categories" surface>

  <Fragment slot="sub">

    Every entry belongs to exactly one of six categories, fixed by the first
    segment of its path: an entry at `gotchas/timeouts.md` is a `gotchas` entry.
    The categories are the single model the whole subsystem is built on.

  </Fragment>

  <Prose nested>

  Each category carries a **retrieval tier** that decides when its entries reach
  the planning agent. There are two:

  - **Always-applied**: `conventions` and `glossary`. Every entry is loaded in
    full on every planning task, and these categories are deliberately excluded
    from search so the same content is never surfaced twice. Keep them small:
    their entire contents are paid for on every task.
  - **Looked-up**: `architecture`, `gotchas`, `learnings`, and `decisions`.
    This is the larger reference body. Entries are retrieved only when a query
    matches them, so the category can grow without weighing down every task.

  The six categories, in the order the registry declares them:

  | Category | Tier | What goes in it | What belongs elsewhere |
  | --- | --- | --- | --- |
  | `conventions` | always-applied | The rules the team always wants honoured: coding standards, naming, formatting, required patterns, house style. Stated as an imperative rule to follow. | The *reasoning* behind a rule (a decision); a one-off lesson (a learning). |
  | `glossary` | always-applied | The shared vocabulary: domain and project terms, each a term plus a one- or two-sentence gloss. | How a thing works (architecture); why a choice was made (a decision). |
  | `architecture` | looked-up | How the system is built and fits together: components, responsibilities, boundaries, and data/control flow. | Why a structure was chosen (a decision); a defined term (glossary). |
  | `gotchas` | looked-up | Sharp edges and non-obvious traps: surprising behaviours and easy mistakes, with what to do instead. | A standing rule (a convention); the system's structure (architecture). |
  | `learnings` | looked-up | Empirical findings from doing the work: what was tried, what worked, what didn't. | A decision with its rationale (a decision); a rule to follow (a convention). |
  | `decisions` | looked-up | The reasoning behind choices (ADR-style): options considered, trade-offs weighed, why one path won. | The resulting structure (architecture); a rule to follow (a convention). |

  The boundaries matter as much as the purposes: they are what let you, and the
  assistant, tell two similar-looking categories apart at the edges, so a
  rule lands in `conventions`, the reasoning behind it lands in `decisions`, and
  the structure it shapes lands in `architecture`.

  </Prose>

</Section>

<Section heading="The lifecycle of an entry">

  <Fragment slot="sub">

    Entries are plain markdown files, and you manage them through the
    `spektacular knowledge` commands: create one, search and read it back, and
    rewrite it when things change.

  </Fragment>

  <Prose nested>

  **Creating.** A new entry is written with `knowledge write`, naming the tier
  and the store to put it in and the path within that store. The content comes
  from a file or standard input:

  ```bash
  spektacular knowledge write \
    --data '{"tier": "repo", "name": "docs", "path": "gotchas/db-timeouts.md"}' \
    --file ./db-timeouts.md
  ```

  The first segment of the path picks the category (`gotchas/db-timeouts.md`
  lands in `gotchas`) and the entry is stored as raw markdown at
  `<location>/<category>/<name>.md`, with any missing parent directories created
  for you. There is no required frontmatter; an entry's title is taken from its
  first heading, falling back to its path.

  **Searching and retrieving.** `knowledge search` runs a keyword query across
  the stores the request covers and returns ranked, one-per-document hits, each
  with a few short excerpts so an agent can scan many results cheaply. Results
  are scored by how often the query terms appear, with ties broken by store order
  and then path, so the ordering is stable. Every hit reports the tier and store
  it came from, which is exactly what `knowledge read` needs, so a result can be
  pulled back in full without a second lookup and with no risk of fetching a
  same-named entry from somewhere else. Add `--tier` and `--filter` to narrow
  what a search covers.

  ```bash
  spektacular knowledge search "database timeout"
  ```

  The two always-applied categories, `conventions` and `glossary`, are
  deliberately left out of search results. They are already loaded in full on
  every planning task (via `knowledge always-applied`), so surfacing them in
  search too would only repeat the same content.

  **Keeping it up to date.** There is no separate update command: you write the
  entry again to the same tier, store name, and path, and the new content replaces
  the old.
  Because entries are identified by the exact bytes of their content, rewriting
  the same text changes nothing, while genuinely edited text supersedes the
  previous version.

  </Prose>

</Section>

<Section heading="Configuration" surface>

  <Fragment slot="sub">

    Which knowledge you mean: the two tiers a store belongs to, how it gets its
    name, and how a request says which stores it covers.

  </Fragment>

  <Prose nested>

  Knowledge lives in one of two tiers. Every registered repository contributes
  exactly one store, holding what is true of that repository's own code. The
  project declares any number of shared stores for knowledge that belongs to no
  single repository, a team handbook say, or a personal one you carry between
  projects. Every request states which tier it means, and names a store within
  it.

  One word does double duty, so it is worth separating now. A *category* has a
  **retrieval tier**, which says when its entries are loaded: `always-applied`
  for conventions and the glossary, `looked-up` for everything else. A *store*
  has a tier in the sense used on this page, which says which knowledge it
  holds. The two are different axes and never appear on the same thing.

  **A repository declares one store.** It lives in the repository's `repo.yaml`,
  so it travels with the repository into every project that registers it.
  Relative locations resolve from the folder holding that file:

  ```yaml
  # repo.yaml
  knowledge:
    provider: file
    config:
      location: knowledge
  ```

  There is no name to set here. The store is addressed by the name the project
  registered the repository under, so the repository does not choose it, and
  there is no list because a repository has exactly one store.

  **The project declares its shared stores.** These are the ones no single
  repository owns, and they live under the `knowledge` key of
  `.spektacular/config.yaml`, each with its own name. Relative locations resolve
  against the project root; absolute paths and `~` work too:

  ```yaml
  # .spektacular/config.yaml
  knowledge:
    sources:
      - name: team
        provider: file
        config:
          location: ~/work/team-knowledge
  ```

  Names must be unique within the project tier. A shared store may reuse a
  repository's name, because a store is identified by its tier and its name
  together, not by the name alone.

  **Addressing a store.** Reading and writing name exactly one store, so they
  take a tier and a name alongside the path:

  ```bash
  spektacular knowledge write \
    --data '{"tier": "repo", "name": "docs", "path": "conventions/site-layout.md"}' \
    --file ./site-layout.md
  ```

  Both the tier and the name are required. A write that leaves either out is
  refused rather than landing somewhere plausible, and the refusal lists the
  names available in that tier so you can reissue it straight away. Run
  `spektacular knowledge sources` to see every configured store by tier and
  name.

  **Narrowing what a request covers.** Searching, listing, and the
  always-applied load take a `--tier` and a repeatable `--filter`:

  ```bash
  spektacular knowledge search "database timeout" --tier repo
  spektacular knowledge search "database timeout" --tier repo --filter docs
  ```

  Omitting the narrowing covers every store the tier reaches, and naming stores
  covers exactly those. No store is ever included or excluded implicitly, which
  is what lets planning work on one repository skip the standing rules of every
  repository it is not touching. Because every store is just a directory of
  markdown files under its category folders, the whole knowledge base stays
  something you can read, edit, and version directly.

  </Prose>

</Section>

<Section heading="Why it works this way">

  <Fragment slot="sub">

    A few deliberate design choices are worth understanding, because they are
    what make the knowledge base trustworthy rather than just convenient.

  </Fragment>

  <Prose nested>

  **Knowledge is a planning-time input, not a runtime one.** The planning agent
  reads the knowledge base while producing a plan and writes the relevant parts
  into the plan itself; the implement workflow then works only from the plan. So
  the knowledge base shapes *what gets planned*, and the plan, not a live lookup,
  is the contract the implementation is held to. This keeps implementation
  reproducible: the same plan builds the same thing, regardless of how the
  knowledge base changes afterwards.

  **One registry is the single source of truth for the category model.** The six
  categories and their tiers are declared once, in code. That single declaration
  scaffolds a new project's directories and READMEs, decides each category's
  retrieval behaviour, and tells the assistant where a new entry belongs. Adding
  a category, or moving one between tiers, is a change in exactly one place.

  **Two tiers, split by how knowledge is retrieved.** Always-applied knowledge
  (conventions, glossary) is the small set every plan must reflect and the
  vocabulary needed to read everything else, so it is loaded in full each time.
  Looked-up knowledge (architecture, gotchas, learnings, decisions) is the
  larger reference body, fetched only when a query matches it. Because tier
  membership lives in that one registry, re-tiering a category is a single,
  self-consistent action: the full-load reader starts including it and search
  stops returning it at the same moment, so the two behaviours cannot drift
  apart.

  **De-duplication is exact, not fuzzy.** When the same knowledge is written more
  than once, the mechanical check for "this is already here" matches on exact
  byte-identity rather than a similarity score. That is deliberate, because
  lexical similarity does not track meaning: *"always retry"* and *"never retry"*
  are nearly identical text but opposite instructions, while *"add jitter to
  retries"* and *"randomize backoff intervals"* share almost no words yet say the
  same thing. Exact matching claims the one thing it can prove, that two entries
  are byte-for-byte the same, and leaves every genuinely semantic judgement to a
  human or the assistant, which is where that judgement belongs.

  **The two tiers answer different questions.** A repository's own store answers
  what is true of that repository's code; the project's shared stores answer what
  spans repositories. Neither overrides the other, so nothing is dropped because
  of where it lives. When two stores hold related knowledge, a refinement is kept
  alongside what it refines and noted rather than hidden, while a genuine
  disagreement is surfaced as a conflict naming both stores instead of being
  silently resolved.

  </Prose>

</Section>
