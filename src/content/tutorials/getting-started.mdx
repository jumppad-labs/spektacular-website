AI coding agents are very good at producing code that looks right. The
problem is that *looks right* and *is right for your codebase* are rarely
the same thing. Hand an agent a product requirement and ask it to
implement the feature, and you will usually get something that runs.
Whether it matches your team's conventions, integrates correctly with the
systems you already have, and uses the current version of every API it
touches is another question entirely.

The common response is to iterate: prompt, review, correct, prompt again.
This works, but it is slow, and it tends to surface the same mistakes
repeatedly. The agent does not learn what your team already knows.

In this tutorial you will see how Spektacular's Spec Driven Development 
workflow improves this itterative process by using a measured and planned 
approach to the feature development.  

We are going to walk through the process end to end adding OAuth2 login to 
an existing Go HTTP API as the example. The example itself does not matter 
much, what matters is the pattern, and the part of the pattern where most runs
succeed or fail: providing the right context.

The tutorial works with every coding agent Spektacular supports — pick
yours at the top of the page and the agent-specific commands and
screenshots swap to match.

## What is Spektacular

Spektacular is a CLI and collection of skills that integrates with your coding
agent and drives Spec Driven Development end to end. It is agent-agnostic, 
it ships with adapters for Claude Code, Bob, and it has a plugable data layer 
that allows you to write your specs and knowledge base in a way that works for you.

There are three agent skills that do the real work:

```bash
/spec-new        # scaffold a new specification
/spec-plan       # turn a spec into a detailed implementation plan
/spec-implement  # drive the agent through the plan
```

Each skill runs as a resumable state machine. You can stop in the
middle of a run, edit a file, and pick the run back up. Nothing is hidden
inside opaque agent state — the spec, the plan, the supporting research
and context documents, and the project knowledge base all live on disk
where you can read and edit them.

## What is Spec Driven Development

Spec Driven Development (SDD) is a methodology for working with AI coding
agents. It increases the quality of an agent's output by following a
simple process that does nothing more than improve the description of
what you want and the context around the system where it will be applied.
As a human working on a task you follow a very similar process: before
starting to code, you form an idea of what needs to be done and, using
your knowledge of the system and the team's practices, you work out where
and how to implement the change.

There are three pillars:

- **Specification** — written by a human, focused on behaviour and
  constraints, never on implementation.
- **Context** — the team's collective memory written down, plus live
  documentation for anything that changes faster than the model.
- **Process** — spec, plan, refine, implement, with a human in the loop
  at every transition.

Done right it feels close to vibe coding, but with sharper output. Let us
set the project up and then walk through each pillar in turn.

## The specification

If you have worked with Product Requirement Documents (PRDs) you will be familiar 
with the process of translating business requirements into a technical specification
that you can turn into code. The specification in Spektacular serves the same purpose,
it is a hint to the agent of what you want to build.

The key with a specification is that it is `what` you want to build not `how` you want to
build it. The how is the agent's job. The process in spec driven development guides
the agent to create the code that satisfies your requirements and does it in a
way ensuring that the code produced is correct and  

The specification in the Spektacular workflow is a markdown file with the 
following sections:
* Overview
* Requirements
* Constraints
* Acceptance Criteria
* Technical Approach
* Success Metrics
* Non-Goals 

The content in these sections is what gudes the agent to create a technical
plan which is then implemented. Spending time on getting the specification right
ultimately saves you time as the plan is more likely to be correct and contain
the features that you actually want to build. It also acts as living documentation
for the features you are buiding and allows you to collaborate with you team
on the initial requirements.

### Overview

The overview is a short two-or-three-sentence summary that answers what is being built,
what problem it solves, and who benefits. For the SQLLite migration the overview
might look like this:

```markdown
Currently the monsters and users are stored in plain text files. We should migrate 
this to a datastore so the system can safely handle updates from multiple threads 
without relying on file writes. This benefits the teams operating and extending 
the service by making data updates more reliable and scalable.
```

In the prompt box for your agent enter the overview and submit it.

Once you submit it the agent will move on to the next section which are the requirements.

Your agent will probably ask you to write to a temporary file. Spektacular writes 
all temporary content and context to disk before creating the final specification or plan.
This enables the workflow to be resumable and also so you can see and edit any of the
working copy.

### Requirements

Requirements are specific, testable behaviours and are written in an Active voice 
("Users can…"). Each item should be independently verifiable, focused on *what* not *how*:

Quite often the agent will assist you with some examples of requirements if if
can infer enough detail from the overview or it may ask you for some clarifying 
questions that help you write better requirements.

<AgentBlock for="claude">
![spec requirements](/images/tutorials/getting-started/requirements-claude.png)
</AgentBlock>

If you answer the questions that the agent asks you it will attempt to generate some 
requirements for you. You can then edit these to make them more specific or add any 
that you think are missing. Below is the list that the agent suggested for me:

```markdown
1. The system must store all monster and user records in a datastore instead of plain text files.
2. The system must migrate all existing monster and user records into the datastore so no existing data is lost.
3. The system does not need to retain the old text files after migration.
4. The system must apply every record update atomically — an update either fully succeeds or has no effect.
5. The system must apply concurrent updates in a well-defined order so simultaneous operations do not interfere with one
another.
6. The system must allow multiple concurrent operations to read and update records safely without data corruption.
7. If a write fails, the system must guarantee no corrupt or partial records and no loss of previously committed data.
8. Every operation available against the existing text-file storage must continue to work identically after the migration.
9. This change introduces no new user-facing capabilities; it is a like-for-like migration.
```

For the purposes of this tutorial we are going to simplify this list to the following requirements.
If the agent has already suggested a list of requirements for you you can tell it to 
replace that list with the simplified one below. If it has not suggested a list yet you can just tell it 
to use this list.

```markdown
- The system must persist monsters and users across service restarts.
- The system must allow multiple threads to update monster and user data safely without corruption.
- The system must return the latest committed monster and user data to readers.
- The system must support creating, updating, and retrieving monster and user records.
- The system must query the datastore on demand instead of loading all monster and user data into memory at startup.
```

Next let's look at the acceptance criteria.

### Acceptance Criteria

Acceptance criteria is binary pass/fail conditions, each traceable to a requirement:

<AgentBlock for="claude">
![spec acceptance criteria](/images/tutorials/getting-started/acceptance-claude.png)
</AgentBlock>

Again the agent has suggested some acceptance criteria based on the requirements and it
is also prompting you to answer some questions that best help it refine this list.
Interestingly the agent is also asking about deletion, which was not one of our
requirement however is a common capability for an API. For this tutorial, let's just
use the following list for the acceptance criteria. 

```markdown
- When the service restarts, previously created monsters and users are still available.
- When multiple updates happen at the same time, all successful changes are preserved without corrupted records.
- When a monster or user record is updated, the next read returns the updated values.
- When a client creates, updates, or retrieves a monster or user record, the operation succeeds and returns the expected data.
- When the service starts, it does not require preloading all monster and user data before serving requests, and requested records are returned from the datastore on demand.
```

Good acceptance criterion lets two independent reviewers run a test and get the 
same yes-or-no answer. An example of bad acceptance criteria would be something like 
*"The API should feel responsive"* this is not independently verifiable as responsive
is subjective based on the testers expectations and experience. If we wanted acceptance
criteria around responsiveness we would make it measureable, for example:
*The API should response to monster read requests within 100ms 95% of the time under a 
load of 100 concurrent users*.

At no point have we defined any technical implementation details. The spec's job is to 
describe what the system must do, not how it does it. The moment you put a code snippet 
in a spec you are making an implementation decision that belongs to the agent.

Constraints are hard boundaries the solution must operate within that cannot be inferred
from context. The agent has done a pretty good job of asking some clarifying questions that
would lead to some constraints for this feature. For example asking about external infrastructure

## Context

This is the section that decides whether the rest of the tutorial works
on your project.

If we think back to a manual software development process, a product
owner creates a business requirement and hands it to a developer to
implement. How the developer translates that requirement into code draws
on two sources of knowledge: what is in their head — their understanding
of the language, the system's history, past architectural decisions, and
conversations with colleagues — and what is written down in
documentation. The most critical knowledge is usually split across both,
with a significant amount living in the collective memory of the team.

The AI agent has only what it can infer. It can read your source and try
to understand your patterns, and it does have a wealth of knowledge from
its training. But it only sees the patterns present in the codebase in
front of it, not those used across your wider application suite. APIs
continually change, and the details used to train a model are not
necessarily current. And the macro environment — how this application
fits within your wider suite — is invisible unless you tell it.

As a developer, before you start coding, you assemble all of this
information. It is often the difference between success and failure. So
if the agent is going to act on your behalf, it needs the same context
you do.

Spektacular gives you four places to put that context. The right answer
is usually some combination of all of them.

### The project knowledge base

The first place is the project knowledge base at
`.spektacular/knowledge/`. This is a directory of plain markdown files
that Spektacular loads into the plan and implement runs. The knowledge
base is the team's collective memory written down — the things that are
obvious to you and your colleagues but not visible from the code.

For the OAuth example, before generating the plan, populate the
knowledge base with the bits the agent could not infer:

```markdown
# .spektacular/knowledge/session-middleware.md

The Go service uses a single session middleware mounted in
`internal/middleware/session.go`. It backs sessions in Redis via
`github.com/redis/go-redis/v9` and signs cookies with the value of
`SESSION_SECRET`. Any new auth flow must reuse this middleware — do not
introduce a second session store. Cookies are configured `HttpOnly`,
`Secure`, `SameSite=Lax` in production; tests rely on `SameSite=Lax` for
the OAuth round trip to work, so do not tighten this without checking
the integration tests in `internal/auth/auth_test.go`.
```

Notice what this file is and is not. It is not architecture
documentation. It is the answer to a specific question — *"how does
session handling work, and what is the trap if you change it?"* —
written for a reader who is about to make a change. The agent will read
this, the answer will be loaded before any planning starts, and the
resulting plan will reuse the right middleware instead of reinventing
one.

### Multi-source knowledge

A single project's knowledge directory is the start, but Spektacular
supports multiple knowledge sources, each scoped:

```yaml
# .spektacular/config.yaml
knowledge:
  sources:
    - scope: project
      provider: file
      config:
        location: .spektacular/knowledge
    - scope: team
      provider: file
      config:
        location: ~/work/team-knowledge
    - scope: global
      provider: file
      config:
        location: ~/spektacular-global
```

When the agent searches for context, Spektacular queries each source in
order and tags every result with its scope. This matters because the
same question can have different answers at different scopes — a *team*
source might say *"we always use `golang.org/x/oauth2` for OAuth and
never third-party auth frameworks like `goth`"*; a *project* source
might say *"this project additionally requires the GitHub flow to allow
only members of the `acme-engineering` org."* The scope tags are visible to the agent, so
when answers conflict it knows which is more specific.

### MCP servers for live documentation

The knowledge base captures what your team knows. The other half — APIs,
SDKs, and libraries whose documentation moves faster than model training
cycles — is best served by Model Context Protocol (MCP) servers. An MCP
server gives the agent a tool it can call to fetch current information
on demand, instead of relying on what was true the last time the model
was trained.

Configuring MCP servers is specific to the agent. For Claude Code you
would add them to `.mcp.json`; Bob and Codex have their own configuration
formats. Spektacular itself does not manage MCP — the agent owns that —
but the project knowledge base is a good place to leave a note for
future contributors about which MCP servers this project expects.

### Skills for domain expertise

The knowledge base captures what your team knows. MCP servers give the
agent a way to fetch what is currently true. *Skills* are the fourth
surface — packaged, reusable bundles of practices and conventions for a
particular domain that the agent loads alongside your project knowledge.

A skill is closer to a discipline than a fact. A "Go HTTP API" skill
might encode practices like *"always thread `context.Context` through
handler chains"* or *"return `http.StatusUnprocessableEntity` for
validation failures, not `400`."* These are the corrections an
experienced reviewer makes on every PR; a skill encodes them once so
the agent applies them by default.

Tessl is a good source of these skills. It is a package manager for
agent tiles, distributing curated bundles for specific domains —
language conventions, provider-specific best practices, popular library
patterns — and benchmarking each tile against a standard evaluation, so
you can see the quality improvement a tile produces before installing
it. For our OAuth example, a Go HTTP API tile and a
`golang.org/x/oauth2` tile would catch the kinds of mistakes a generic
model makes when writing idiomatic Go — wrong context propagation,
leaked goroutines on cancelled OAuth flows, ad-hoc error handling that
diverges from the rest of the codebase.

Skills are managed by the agent rather than by Spektacular — for Claude
Code, Tessl installs tiles into `.tessl/` and references them from
`AGENTS.md`, which Claude loads automatically. The split between
surfaces is worth keeping in your head: knowledge files are *yours*,
skills are *shared*, and MCP is *live*. The agent benefits most when you
provide all three on top of the codebase itself.

### Why context decides the outcome

Here is the concrete failure mode. Without the session-middleware note
above, an agent generating an OAuth implementation will look at the
codebase, see *some* session handling, and produce a plausible plan that
often wires a second session store (frequently `gorilla/sessions`) into
a parallel middleware chain for the OAuth routes. The integration tests
will pass because each session stack handles its own cookies. Production
will fail interestingly the first time a user who logged in via OAuth
hits a handler that reads the original session.

The fix in code is trivial. The fix in process is to write the note
once, put it in `.spektacular/knowledge/`, and never have to catch the
same mistake in plan review again. Context investment compounds: every
note you add raises the floor for every future plan against the same
codebase.

<TutorialStep number="5" heading="Populate the knowledge base">

  Before generating the plan, walk your codebase looking for the
  load-bearing facts the agent would not infer — session handling,
  shared middleware, the schema rule that breaks downstream consumers,
  the test files that quietly rely on a particular config value. Write
  each one as a short, focused markdown file under
  `.spektacular/knowledge/`.

  ```bash
  $EDITOR .spektacular/knowledge/session-middleware.md
  $EDITOR .spektacular/knowledge/auth-conventions.md
  ```

  Three or four well-targeted notes is usually enough to see the
  difference in the very first plan. Treat the knowledge base as a
  living document — add to it whenever you correct the agent on
  something a future run would benefit from knowing.

</TutorialStep>

## The plan

The plan is the technical implementation blueprint of what the agent
will produce. It provides enough detail to give you a firm idea of
direction and enough context for the implementation itself.

<TutorialStep number="6" heading="Generate a plan">

  Pass the spec name returned by `spec new`. Spektacular loads the spec,
  the knowledge base sources, and any agent-side configuration, then
  drives the agent through an exploration phase. It reads the parts of
  the codebase the spec touches, looks up your knowledge-base notes,
  queries MCP for current API signatures, and surfaces clarifying
  questions when it finds gaps.

  ```bash
  spektacular plan new --data '{"name":"<returned-spec-name>"}'
  ```

  Answer the questions in your terminal and the run continues. The plan,
  along with supporting `research.md` and `context.md` documents, lands
  in `.spektacular/plans/<id>_oauth-login/` when it is done.

A plan looks something like this:

```markdown
# Plan: OAuth Login (000001_oauth-login)

## Overview
Add Google and GitHub OAuth flows to the existing Go HTTP API using
`golang.org/x/oauth2`, integrating with the session middleware in
`internal/middleware/session.go`. Local-password authentication remains
unchanged.

## Phases

### Phase 1 — Wire OAuth into the existing session middleware
- Add an `OAuth` service in `internal/auth/oauth.go` that wraps an
  `oauth2.Config` per provider.
- Mount the OAuth handlers under `/auth/...` *after* the session
  middleware on the chi router so they share the Redis-backed session.
- Resolve or create the local user record by provider email inside the
  callback handler.

### Phase 2 — Add provider routes
- Add `GET /auth/google`, `GET /auth/google/callback`,
  `GET /auth/github`, `GET /auth/github/callback` to the chi router in
  `internal/auth/routes.go`.
- Callbacks use the project's existing `flash` helper for the
  cancel/error path so the error surface stays consistent with the
  local login flow.
```

Further down, the plan carries forward the things your knowledge base
told it — for our example, the cookie-config note appears as an explicit
instruction not to modify `sameSite` because the integration tests rely
on it. With a vibe-coding approach this kind of detail would not surface
until the final code was produced, and you would discover the trap by
breaking integration tests. The plan stage is where that conversation
happens cheaply.

<TutorialStep number="7" heading="Refine the plan">

  However good your spec and context are, you will not always get a
  perfect plan first time. Correcting it is trivial: you talk to your
  agent the way you would talk to a colleague. *"We are missing a test
  for the cancel path on the GitHub flow — can you add one?"* *"Our
  naming convention for integration tests is
  `<feature>_integration_test.go`."* The agent updates the plan, you
  check it again, and once you are happy you move on.

  Spektacular's plan stage is resumable, so you can stop, edit the plan
  or a knowledge file directly, and pick up where you left off. If a
  correction reveals something that would help every future plan against
  this codebase, write it into `.spektacular/knowledge/` while you are
  there. Future runs benefit immediately.

</TutorialStep>

## Implementation

<TutorialStep number="8" heading="Implement the plan">

  Pass the plan name returned by `plan new`. Spektacular drives the
  agent through each phase of the plan in turn, ticks off acceptance
  criteria as they pass, and writes a per-phase changelog into the plan
  document.

  ```bash
  spektacular implement new --data '{"name":"<plan-name>"}'
  ```

  If a criterion is not yet satisfied, the run does not advance until

  it goes, and because everything is on disk you can interrupt at any
  point, hand-edit anything that looks off, and resume.

## What's next

Spec Driven Development is not a productivity hack and it is not a way
to remove humans from the loop. It is a way of front-loading the
conversation about *what* you want and *what your system already does*
into a place the agent can actually use, so that the implementation step
becomes the boring one. The three pillars stay the same regardless of
which tool you use:

- **Specification** — written by a human, focused on behaviour and
  constraints, never on implementation.
- **Context** — the team's collective memory written down, plus live
  documentation for anything that changes faster than the model.
- **Process** — spec, plan, refine, implement, with humans in the loop
  at every transition.

Start the next feature with a new spec. As you go, add to
`.spektacular/knowledge/` whenever you correct the agent on something a
future run would benefit from knowing — every note you add raises the
floor for the next plan.
